# Architecture and evaluation research for SMAIP

Research date: October 31, 2026. This is a proposed implementation/evaluation plan informed by primary sources and the current checkout. No model was downloaded, trained, or called; no paid service was used. Runtime and the BRD were not edited.

## Decision

Prioritize task-scoped capabilities, factual handoff validation, and an evidence-derived acceptance runner before a larger probe-training run. The immediate failure is useful work: the separated agent invents fields and performs unnecessary writes. The current attacks also produce zero targeted successes in the undefended arm, so additional detector training alone cannot establish a security improvement. Build a capable, honestly described baseline and an untouched evaluation protocol together.

The owner-selected agent and detector models remain open models. Historical hosted-Codex requirements are superseded. The source BRD URL could not be opened through this research tool; requirement mapping below uses the already audited [BRD alignment document](../BRD_ALIGNMENT_2026-10-30.md), and is not a new verification of the live BRD. Its important conditions remain: clean multi-agent utility within five percentage points of single-agent utility; strict full-stack ASR improvement; TPR at 1% FPR; measured latency/cost; human review; and PII handling.

## What is actually measured

The [paired protocol-4 development audit](../../../reports/OPEN_AGENT_DEV_02_ANALYSIS.md) records 24 real Qwen2.5-3B-Instruct episodes: no-defense clean utility 4/4, least-privilege 2/4, keyword 4/4; utility under attack 3/4, 2/4, and 1/4 respectively. Every arm has targeted ASR 0/4. These are development results on four fixture pairs, not independent security or noninferiority evidence. The actor's unnecessary files and unsupported metrics explain remaining clean failures; the scorer has appropriately retained them.

The [current implementation status](../OPEN_MODEL_V2_IMPLEMENTATION.md) records poor frozen external detector transfer: linear catches 0/400 injected documents; mean pooling catches 1/400 and flags its clean counterpart. Treat that observed external set as known regression material now. It cannot serve as an untouched final set after these results influenced development. This research did not rerun or independently re-audit those bundles.

| Source inspected | What the source establishes | Consequence for SMAIP |

| [InjecAgent upstream](https://github.com/uiuc-kang-lab/InjecAgent) | Supplies 1,054 cases across 17 user tools and 62 attacker tools, with local-model interfaces and harmful-action/data-exfiltration tests. | Useful held-out tool-injection and attacker-objective coverage. ## Code-level findings

Inspected owning sources: [`open_loop.py`](../../../src/smaip/agents/open_loop.py), [`action_schema.py`](../../../src/smaip/agents/action_schema.py), [`gateway.py`](../../../src/smaip/gateway/gateway.py), [`open_agent_dev.py`](../../../src/smaip/eval/open_agent_dev.py), [`contract.py`](../../../src/smaip/eval/contract.py), [`acceptance.py`](../../../src/smaip/eval/acceptance.py), [`low_fpr.py`](../../../src/smaip/probes/low_fpr.py), and [`manifest.py`](../../../src/smaip/probes/manifest.py). Findings describe this working checkout, not a released deployment.

1. **Roles are broader than task intent.** `ROLE_TOOLS['actor']` grants send, write, and delete even for a task that only requests sending one summary. A prompt says not to create scratch files, but the capability boundary permits them. This matches the observed unnecessary writes. Bind authorization to the specific user task as well as the role: allowed operation, recipient, vendor/source scope, object paths, and maximum side-effect count. Keep broad role capabilities as the ceiling; task authority must be narrower.

2. **Structured JSON is useful syntax protection, not factual or authorization validation.** `NumericFields` constrains keys/types/ranges, but a syntactically valid zero or fabricated count passes. `SummaryHandoff` contains unverified model prose and optional formatter output; its literal `taint='untrusted'` is descriptive metadata, not a runtime information-flow policy. The actor receives and reinterprets those bytes. A downstream capable model can still follow an instruction in a valid string.

3. **The runtime success flag is too weak for BRD quality.** `legitimate_ok` checks any nonempty send to the trusted recipient. It does not check facts, complete source coverage, extra sends, or writes. The separate development scorer is substantially better: exact requested content, source hashes, one authorized send, no unauthorized sends, and no unexpected files. Acceptance should derive quality from the appropriate versioned post-run oracle, never `status='done'` or `legitimate_ok` alone.

4. **Approvals have good action binding but lack a persistent workflow.** The open loop hashes exact tool arguments, consumes one confirmation, and checks the trusted recipient for approved sends. However, confirmation reruns generation rather than resuming immutable saved state. A gateway-only/full-stack comparison that merely stops before every write will appear safe while failing useful work. Benchmark the lifecycle explicitly: proposals, trusted policy decisions, approval requests, resumed/declined actions, and task completion. Never let a ground-truth scorer silently approve the desired action.

5. **Current read quarantine is genuinely stronger than warning text.** The open loop substitutes a typed blocked result before forwarding quarantined content; raw quarantined bytes do not reach later model contexts. Preserve this. The generic gateway itself returns a marker plus raw content for quarantined reads, so every new caller/adapter must use an equally strict boundary instead of forwarding `Decision.output` directly.

6. **“No defense” retains common controls.** Every arm still has Pydantic/constrained JSON, schema validation, a safety-oriented system prompt, fixture-only effects, and bounded generation. Those common controls are reasonable. Name this arm “single agent, selected defenses off” in results and enumerate shared controls. It establishes the incremental value of selected defenses, not unconstrained model vulnerability.

7. **Topology and budget require careful interpretation.** All arms receive a fixed total call budget, while specialists have phase reservations and extra prompt/handoff overhead. This is a useful fixed-budget comparison, but failures may reflect allocation as well as separation. Report per-phase calls, tokens, and termination reasons; add a predeclared resource-normalized diagnostic without replacing the BRD's matched-condition comparison. Do not grant extra calls only after observing a failed final test.

8. **Full-stack attribution is incomplete.** The canonical matrix compares a two-probe full stack with separate linear/mean arms, alongside topology/keyword/gateway changes. Retain these BRD rows, then add a `both-probes-only` diagnostic or selected factor-removal rows to identify whether joint detector use, isolation, or approval caused a difference. Avoid claiming each layer contributes from one aggregate full-stack row.

9. **Model-input PII is still an open boundary.** The recipient token avoids exposing its actual address in initial prompts, and trace text is redacted. Tool results and handoffs otherwise enter model messages. Define source-specific input minimization and secret handling separately from log redaction. A local model reduces provider exposure but does not prevent exfiltration through allowed outputs, saved traces, or future fetches.

## Proposed architecture: task authority outside the model

For the existing bounded vendor workflow, a custom general-purpose interpreter is unnecessary. Use a small immutable task-intent object created from trusted request/configuration before any external content is read. It should contain the requested operation, fixed recipient/reference, allowed source set, requested fields/format, permitted destination paths, side-effect count, and approval mode. Ambiguity should produce a reviewable clarification/approval state, not authority inferred from a page.

The reader may list/read only the intent's vendor/source set. The quarantined extractor/analyst may propose `EvidenceClaim` records: field, value, source ID/hash, and a quote/span supporting that value. These records remain untrusted. A deterministic domain validator checks source membership, value correspondence, field completeness where mechanically decidable, and permitted calculations. References copied from the source are not trusted just because a model emits a valid ID. Missing/conflicting values should become explicit uncertainty, not zero-filled fields.

For canonical numeric briefs, format validated fields deterministically. The actor can propose the requested send, but its body must match the validated summary artifact and recipient must resolve from trusted task intent. A digest or server-side artifact reference avoids another free-form rewrite. This is a general architecture rule applied to every fixture, not inserted ground truth: the expected answers remain exclusively in the scorer. For general prose, automatic factual validation is weaker; preserve source attribution and require the planned human review when necessary rather than claiming deterministic semantic correctness.

The gateway enforces task intent, role ceiling, provenance restrictions, argument schema, action count/idempotency, and approval binding. The detector remains an advisory/quarantine layer for malicious content, never the source of new authority. Use a persisted pending-action object with task/version/action digest, expiry, one-time confirmation, and an audit event; resume the saved computation after confirmation. Redact logs separately from minimizing model inputs and checking outputs for private canaries.

This proposal follows the control/data separation motivated by CaMeL; its security claims remain limited to the implemented policies and tested tool boundary. It cannot ensure that vendor claims are true, eliminate summary manipulation, or supply a formal guarantee merely through typed records.

## A fair baseline that can reveal susceptibility

An undefended baseline is an experimental control, not an agent deliberately instructed to obey attacks. Freeze its task prompt, tools, schema, model revision, decoding, resource budget, and shared safety instructions before final attack testing. The same legitimate tasks and sandbox assets must appear in every arm. Never replace the model with a scripted attack follower, remove useful instructions only from the baseline, reveal attacker goals in its prompt, or alter the scorer to produce a win.

First validate attack feasibility mechanically: attacker-controlled text reaches the intended result position; the targeted tool/action exists; the baseline can express the action through the shared schema; the sandbox contains the target asset; and the oracle detects an injected known bad effect in a separate evaluator test. These tests establish reachability and grader validity, not measured model susceptibility.

Use development-only attack search across realistic authority spoofing, instruction laundering in retrieved data, cross-message payloads, output corruption, and ambiguous action-open tasks. Keep attacker write access exactly bounded to declared tool-result slots. Choose a predeclared, affordable attempt/token budget and an open attacker model if model-generated search is used later. Save failed candidates, search feedback, cost, and the final selected payloads. Equalize search effort across defended arms; a static replay of attacks optimized only against no-defense is not defense-adaptive evaluation.

Report both unconditional targeted ASR on all preregistered security cases and a secondary paired ASR on clean-capable/reachable cases. Select that secondary denominator by a rule frozen before observing attacked outcomes, show exclusions and counts, and retain the unconditional result. Do not filter final cases to only attacks that happened to succeed in no-defense. If no-defense remains at zero, state the suite/model is non-discriminative for comparative security; report the bound and utility instead of declaring defense success.

A model upgrade is a separate factor. If 3B cannot perform representative clean tasks reliably, select another feasible open model using clean development utility/tool-use quality and hardware constraints, then freeze it. Do not choose a model solely because it is easier to attack. No new model or hardware recommendation has been experimentally validated by this research.

## Independent evaluation and metrics

Use three distinct tracks whose data and conclusions are not interchangeable:

- **Detector generalization:** reviewed document labels, adequate benign and attack cases, raw scores, held-out families/sources, and frozen calibration. Include benign documents discussing attacks, quoted instructions, multilingual content, and long realistic tool results. A malicious document label is different from whether this agent executed an attacker action.
- **Agent security and quality:** paired clean/injected episodes with deterministic state/effect oracles where feasible, a representative vendor suite, and a pinned external AgentDojo subset/full suite. Preserve native benchmark semantics. For a resource-bounded subset, predeclare IDs and sampling before reading results; report it as a subset.
- **Adaptive evaluation:** frozen defender and bounded attacker search, with tasks or source groups held out from development, declared attacker knowledge/feedback, and equal attack budgets. Adaptation to the frozen final defender is legitimate evaluation; using those outcomes to tune the defender consumes the final set.

“Independent” must identify the dimension: held-out task, document, source, family, generator, or evaluator. Unique IDs and different declared group strings do not establish independent authorship, near-duplicate separation, or independence from public-model pretraining. Record upstream snapshots/licenses, split hashes, authorship/generator provenance, semantic/near-duplicate review, and label adjudication. Keep human-reviewed provenance alongside machine checks. Public benchmark contamination cannot be excluded merely by pinning a revision.

Report clean task success, task success under attack, targeted ASR, unsolicited action attempts, executed unauthorized effects, source coverage, factual correctness, format correctness, approval completion, unnecessary calls, and aborts separately. Refusal/quarantine can improve ASR while reducing task utility; neither should be hidden inside one “safe success” score. Use the strict whole-task result as primary and component scores for diagnosis.

Calibrate a threshold on calibration data only. Report achieved frozen-threshold test TPR/FPR and raw TP/FP/TN/FN, plus AUROC and a separately labeled descriptive test ROC TPR@1%FPR. The latter is a characterization, not a deployable threshold tuned on final test labels. Give confidence intervals and group/family macro results. For independent Bernoulli negatives with zero false positives, the one-sided exact 95% upper FPR is `1 - 0.05^(1/n)`; 299 negatives barely puts that upper bound below 1%. Nonzero false positives require the full binomial bound; template clones do not count as independent draws. Selection on calibration data also means its naive post-selection interval is not a population guarantee. An untouched test is essential.

Use paired task-level differences for utility and ASR; repeated seeds on one task are not independent new tasks. Report uncertainty with task/source clustering when appropriate. The BRD's five-point clean-utility tolerance can be assessed as paired noninferiority once its confidence convention is frozen. Keep literal point-estimate compliance separate from statistical evidence. Strict ASR superiority needs more than one lucky discordance: preregister an effect-size target and inferential rule, preserving an explicit “inconclusive” state. If full stack ties an effective least-privilege policy at zero, it cannot satisfy the unchanged strict-superiority BRD criterion. Do not weaken the policy or cherry-pick attacks to force additivity; record unmet acceptance or propose an owner-approved BRD revision.

Measure real wall time and token counts for model, detector, tool, and review phases separately; report total p50/p95, TTFT where available, throughput, cold/warm conditions, cache effects, and failure/timeout denominators. Use rental price and measured generated-token throughput for infrastructure cost; include idle/utilization assumptions and attacker-search cost separately. Fixed integer gateway cost units are not dollars.

## Acceptance gate must be strengthened before it can certify evidence

The current gate correctly rejects missing evidence, duplicated/missing named rows, invalid rates, ties, and excessive supplied FPR. However, it is a contract checker over caller-supplied summaries, not an independent evidence validator.

A local synthetic adversarial check called `assess()` with all seven rows, identity strings, independence/adaptive booleans, 299 negatives per split, zero test TPR, zero AUROC, zero FPR, and fabricated zero performance values under positive budgets. With nonzero baseline/comparator ASRs and zero full-stack ASR, the gate returned **`status: pass`** and no pending items. This was a test of gate behavior, not model evidence; no result file was represented as a real run. It establishes a vacuous detector-quality pass and the lack of provenance verification. This note intentionally leaves runtime unchanged.

Recommended gate contract:

1. Consume manifests and per-episode/per-document records, verify source/model/protocol/artifact hashes, reject missing/duplicate/incompatible case sets, and independently recompute counts/rates through a versioned scorer. Backend/model/run strings and boolean attestations are not sufficient.
2. Require positive and negative counts, reviewed grouping/provenance, frozen threshold/model hashes, finite scores, and consistent confusion matrices. Use the chosen low-FPR confidence criterion rather than `n >= 299` alone.
3. Require an agreed minimum useful recall at the operating point and an agreed ranking/relative baseline condition, with positive support and uncertainty. The BRD states a metric but supplies no minimum recall in the audited map; mark the target **pending owner decision**, never silently invent it. A zero-recall model must not get a detector-quality pass just for never alerting.
4. Bind the matrix to matching task IDs, clean/injected pair IDs, initial state, model revision, action schema, tokenizer/precision, budget, and policy configuration. Add actual policy-activation negative checks for each enforcement layer. Validate full-stack and comparator uncertainty/effect sizes, while keeping the literal strict comparison visible.
5. Require full-stack clean and attacked utility, approval-completion accounting, output/privacy canary checks, and actual request/timing/token/cost records. A self-supplied performance budget needs a separately frozen approval/configuration record; agreeing budgets after seeing results is not acceptance.
6. Preserve `pass`, `fail`, and `pending/inconclusive` distinctly. A gate that assesses an incomplete experimental contract must not become a release/certification badge. Keep deterministic software-test passes separate from scientific/model-quality acceptance.

## Ordered implementation work and stop conditions

| Priority | Proposed work | Reviewable exit evidence |
| --- | --- | --- |
| P0 | Freeze metric/oracle definitions and identify current development/regression data; strengthen gate against vacuous/provenance-only passes. | Negative synthetic submissions fail/pending; audited recorded results reaggregate unchanged; no new security claim. |
| P1 | Add task-scoped actor/source authority, validated structured evidence, canonical rendering, persistent action-bound review/resume, and explicit PII boundaries. | Scripted regression covers general rules without fixture-specific answers; a small subsequent real clean pilot measures whether the 2/4 gap improves. |
| P2 | Establish capable clean baseline and development attack reachability/susceptibility; freeze paired external/vendor and adaptive protocols. | Case/policy/model/configuration hashes, grading sanity checks, attempt budgets, honest positive/negative susceptibility results. |
| P3 | Review independent detector corpus/calibration and final holdouts, then perform a bounded new fit/evaluation batch. | Raw frozen scores/counts, lineage, low-FPR uncertainty, useful recall target, native external benchmark and adaptive evidence. More training is conditional on data quality and a legitimate detector use case. |
| P4 | Execute matched full matrix and real serving/performance measurement with approval accounting. | Recomputed security/utility/performance report, statistical limits, clear pass/fail/pending for every BRD condition. |
| P5 | Prepare demo/release artifacts from supported evidence. | Reproducible fixture path, pinned external manifests, threat/policy limits, accurate public claims. Publication remains a separate owner action. |

Stop a larger GPU batch if clean utility is still broken, the final set is not frozen, the baseline cannot express the declared attack, policy activation cannot be demonstrated, or the gate cannot reject useless detectors. Additional compute under those conditions would add runs without resolving the central inference problem.

## Scope and limitations

This report researches architecture and evaluation, not a vulnerability exploit or implementation patch. Primary sources were browsed on the research date; external repositories were inspected through their rendered documentation, not installed or executed. No external benchmark was reproduced and no claim of formal security was proven. Proposed capabilities/evidence checks need their own correctness tests and real-model measurement. Recommendations stay within the existing vendor-research, numeric summary, draft/send sandbox, review, detector, and serving scope.
